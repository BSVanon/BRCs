# BRC-180: Overlay Service Discovery at an Internet Domain

David Case (david.case@shruggr.cloud)

## Abstract

This document specifies how an internet domain declares which overlay services it hosts. A domain publishes a `metanet.overlays` object in its `/manifest.json`, mapping [BRC-22](./0022.md) topic manager names and [BRC-24](./0024.md) lookup service names to the base URL that serves them. A client holding a URL that names a domain can then find that domain's overlay without configuration, out-of-band agreement, or a global search.

## Motivation

Application URLs name domains. A user is given `example.com` and expects a client to work out the rest. When the resource behind that URL lives in an overlay network, the client must discover which host serves the relevant topic before it can submit or query anything.

[BRC-88](./0088.md) already answers a different question well. Its SHIP advertisements let any participant ask "which hosts serve this topic?" and receive a list gathered from across the network. That is the right mechanism for finding hosts in general, and for redundancy when one goes away. It does not say whether a particular domain is among them, and a client resolving `example.com` is not asking for a list — it is asking what that domain runs.

A domain's overlay is also routinely hosted separately from its website. Static site hosting is a poor fit for serving arbitrary content and long-lived streams, so the two commonly live on different hostnames or different providers. Without a declaration, a client is left guessing at conventions such as an `api.` prefix, which fails as soon as an operator chooses differently.

[BRC-68](../peer-to-peer/0068.md) established that a domain publishes machine-readable details about itself at `/manifest.json`, and [BRC-73](../wallet/0073.md) and [BRC-169](../peer-to-peer/0169.md) have since added their own objects to that document. This specification adds one more, for overlay services.

## Specification

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY in this document are to be interpreted as described in RFC 2119.

### 1. The manifest object

A domain hosting overlay services MUST publish a `metanet.overlays` object in the `/manifest.json` served at its root, alongside any other `metanet` objects it publishes.

```json
{
  "name": "Example",
  "metanet": {
    "overlays": {
      "tm_example": "https://api.example.com",
      "ls_example": "https://api.example.com"
    }
  }
}
```

1. Each key is the name of a service, exactly as it is named in submission and lookup requests: a [BRC-22](./0022.md) topic manager or a [BRC-24](./0024.md) lookup service, following the naming conventions of [BRC-87](./0087.md). Those conventions distinguish the two, so no further structure is required here.
2. Each value is the absolute base URL of the host serving that service. It MUST use the `https` scheme, MUST NOT carry a path, query or fragment, and MUST NOT end in a trailing slash. A client MUST reject a value that does not meet these conditions and treat that entry as absent.
3. Different services MAY name different hosts. A domain MAY declare a service hosted on a domain it does not control.
4. The object carries base URLs only. Route paths are defined by BRC-22, BRC-24 and the specification of the service in question, and MUST NOT be specified here. An implementation that needs a path the service's own specification does not define is not interoperable.
5. A client MUST ignore keys it does not recognise, so that a domain may declare services beyond those the client implements.

### 2. Client behaviour

1. To resolve a domain, a client fetches `https://<domain>/manifest.json` and reads `metanet.overlays`.
2. If the document is absent, is not valid JSON, has no `metanet.overlays` object, or that object has no entry for the service sought, the domain does not offer that service. The client MUST NOT fall back to probing hostnames, guessing prefixes, or contacting a host the user did not name.
3. On finding an entry, the client uses its base URL for that service, applying the routes defined by the relevant specification.
4. A client MAY cache the document. In the absence of HTTP cache directives it SHOULD NOT cache for longer than one hour, and SHOULD cache a failed or absent result for a shorter period so that a newly published manifest is picked up promptly.
5. A client SHOULD treat a manifest fetch as untrusted input: bound the response size, apply a short timeout, and never let a failure or a malformed document abort the surrounding operation with anything other than "this domain does not offer that service".

### 3. Relationship to BRC-88

This mechanism and SHIP answer different questions and are complementary.

| | Question answered | Scope |
| --- | --- | --- |
| This document | What does *this domain* host? | One domain, declared by its operator |
| [BRC-88](./0088.md) SHIP | Which hosts serve *this topic*? | The whole network, discovered on chain |

A client resolving a domain-shaped URL SHOULD use this mechanism. A client seeking redundancy, or hosts for a topic with no particular domain in mind, SHOULD use SHIP. A client MAY use both: resolve the domain the user named, and fall back to SHIP when that host is unreachable.

Neither mechanism authenticates the relationship between a domain and a host. A domain declares what it chooses to declare, secured by control of the domain and its certificate, exactly as with [BRC-68](../peer-to-peer/0068.md) and [BRC-169](../peer-to-peer/0169.md). A client MUST NOT infer from this declaration that the named host is trustworthy, only that the domain claims it.

## Example

A repository URL of the form `<scheme>://example.com/<identifier>` is resolved by fetching `https://example.com/manifest.json`:

```json
{
  "name": "Example",
  "metanet": {
    "trust": {
      "name": "Example",
      "publicKey": "0371f0ec5992a9d38e09fe528e367890969c66eaebdb01b4d35a2fc0d61251b3f9"
    },
    "overlays": {
      "tm_example": "https://overlay.example.com",
      "ls_example": "https://overlay.example.com",
      "tm_other": "https://other-host.example.net"
    }
  }
}
```

The client reads `tm_example`, submits transactions to `https://overlay.example.com` per BRC-22, and queries `ls_example` at the same host per BRC-24. It reaches a different operator entirely for `tm_other`, because the domain said so.
